# ECRS Banking Process Reviewer

## 这个 Skill 做什么

对银行内部流程进行 **ECRS 四维度审阅**，识别冗余、瓶颈和改进机会，输出结构化的审阅报告与可落地的优化方案。

**ECRS 四个维度**：

| 维度 | 英文 | 核心问题 | 优先级 |
|------|------|----------|--------|
| **取消** | Eliminate | 这个环节/审批/文档是否真的必要？去掉会怎样？ | 最高 |
| **合并** | Combine | 哪些步骤/角色/表单可以合并？ | 高 |
| **重排** | Rearrange | 步骤顺序是否合理？能否并行？ | 中 |
| **简化** | Simplify | 能否自动化、标准化、降低复杂度？ | 基础 |

ECRS 的审阅顺序很重要——**必须先问"能否取消"，再问"能否合并/重排/简化"**。对一个本可取消的环节做简化是浪费。

## 何时使用

**合适的场景**：
- 银行内部流程效率低下，需要诊断瓶颈
- 新制度上线前做流程预审阅
- 监管检查后发现流程冗长，需要瘦身
- 数字化转型前做流程基线评估
- 跨部门流程存在大量等待/返工
- 用户提供长文档（制度文件、SOP、流程手册）需要审阅

**不合适的场景**：
- IT 系统性能优化（这是技术问题，不是流程问题）
- 外部监管强制要求的合规节点（不能取消/简化，只能优化执行方式）
- 纯系统操作指导（不是流程审阅）

## 长文档分段处理策略

**当用户输入的文件或文档超过 3500 字时，必须使用分段处理**，避免因文本过长导致注意力稀释和信息遗漏。

### 分段原则

1. **按流程边界切分**：不要按固定字数硬切，而是找到流程/章节/制度的自然边界，将同一流程的内容保持在同一片段内。
2. **每段不超过 3500 字**：单个片段的文字量控制在 3500 字以下，确保分析时的注意力集中。
3. **保留上下文**：每个片段必须携带流程的全局信息（流程名称、目的、涉及角色），避免因脱离上下文导致误判。
4. **交叉步骤需重复**：如果某个步骤出现在两个片段的交界处，在两个片段中都包含该步骤的完整描述。

### 分段处理流程

```
Step A. 扫描全文 → 识别流程/章节边界 → 规划分段方案
Step B. 向用户确认分段方案（列出每段覆盖的范围和字数）
Step C. 逐段分析：
    - 对每段独立执行 Step 1-3（获取流程描述 → 建模 → ECRS 审阅）
    - 记录每段的发现和建议
Step D. 合并所有段的分析结果：
    - 去重：同一条建议如果在多段中都出现，只保留一次
    - 关联：识别跨段的全局性问题（如贯穿多个子流程的重复审批）
    - 汇总：生成完整的审阅报告
```

### 分段时的全局上下文模板

每个片段分析时，头部携带以下全局信息（从全文提取，不超过 200 字）：

```
[全局上下文]
流程名称: [X]
流程目的: [Y]
涉及角色: [A, B, C]
本文档总段数: N，当前为第 M 段
本段覆盖: [子流程/章节名称]
```

## 工作流

### Step 1 · 获取流程描述

审阅前需要用户输入流程信息。如果用户还没给，按以下清单收集：

**必填信息**：
- **流程名称**：如"个人消费贷款审批流程"
- **流程目的**：这个流程要达成什么业务目标
- **流程触发条件**：什么事件启动这个流程
- **最终产出**：流程结束时产出什么

**关键信息**：
- **详细步骤清单**：每一步的编号、名称、执行角色、输入、输出
- **角色清单**：涉及哪些岗位/部门
- **审批节点**：哪些步骤是审批/签字/盖章
- **等待/排队环节**：哪些步骤存在等待时间
- **返工/退回环节**：哪些步骤可能退回重做
- **涉及的系统/表单**：用什么工具执行
- **时效要求**：是否有 SLA 或时效考核

**运行环境适配**：
- **在 Claude Code 中**：通过 Ask Question 收集信息，支持用户粘贴现有流程图/SOP 文档/制度文件
- **在其他环境中**：直接对话收集，一次最多问 3-5 个关键问题

如果用户已经有了完整流程文档（SOP、流程图、制度文件），直接读取并开始审阅，跳过信息收集。

**长文档判断**：读取文档后立即评估字数。超过 3500 字则进入"长文档分段处理策略"，向用户说明分段方案并获得确认后再开始分析。

### Step 2 · 流程建模

将用户输入的流程信息整理为**标准化流程模型**，作为后续审阅的基础。

```
流程: [名称]
目的: [目的]
触发: [触发条件]
产出: [最终产出]

步骤:
  S01: [步骤名] | 角色: [岗位] | 输入: [X] | 输出: [Y] | 类型: [操作/审批/等待/流转]
  S02: ...
  ...
```

**步骤类型分类**（后续 ECRS 分析需要）：
- **操作类**：实际执行的工作（录入、调查、核实、计算）
- **审批类**：审批、签字、盖章、确认
- **等待类**：排队、等待、排期
- **流转类**：传递、移交、报送、归档
- **检查类**：复核、校验、比对

建模后向用户确认流程是否完整准确，再进行 ECRS 审阅。

### Step 3 · ECRS 四维度审阅

对流程模型依次进行四个维度的审阅。每个维度都需要：
1. 逐步骤分析
2. 给出判断依据
3. 标注风险等级

#### 3.1 Eliminate · 取消分析

这是最重要的一步。对每个环节问：

**判断清单**：
- [ ] 这个环节的直接产出是否被后续步骤实际使用？（不被使用的产出 = 可以取消）
- [ ] 这个审批是否因历史原因存在但已无实际把关价值？（形式审批 = 可以取消）
- [ ] 这份文档/表单是否和其他文档有大量重复？（重复录入 = 可以取消）
- [ ] 这个检查是否已被系统自动完成？（人工重复检查 = 可以取消）
- [ ] 这个签字/盖章是否因电子化而不再必要？（纸质签章电子化 = 可以取消）
- [ ] 这个报送是否接收方实际不看？（无效报送 = 可以取消）
- [ ] 这个复核是否与前面的操作由同一人完成？（自我复核 = 可以取消）

**银行流程中常见的可取消环节**：
- 多头重复审批（同一笔业务经过 3-5 级审批，实质把关在前两级完成）
- 重复录入（同一份信息在多个系统/表单重复填写）
- 无效报送/抄送（报送后无人处理或系统已自动通知）
- 纸质签章（已有电子签名/电子印章）
- 形式性复核（不产生实质判断的"走过场"检查）
- 过期制度要求的环节（制度已更新但流程未同步）

对每个可取消的环节，标注：
- **取消依据**：为什么认为可以取消
- **风险评估**：取消后是否影响合规/风控
- **依赖条件**：取消需要什么前提（如制度修订、系统改造）

#### 3.2 Combine · 合并分析

对剩余的环节，分析是否可以合并：

**判断清单**：
- [ ] 多个步骤是否由同一角色在同一时间执行？（可以合并为一步）
- [ ] 多个表单是否采集相同或高度重叠的信息？（可以合并表单）
- [ ] 多级审批是否可以合并为一级或授权审批？（可以合并审批）
- [ ] 多次检查/核实是否可以一次性完成？（可以合并检查）
- [ ] 跨部门的同一类操作是否可以集中处理？（可以集中化）

**银行流程中常见的可合并环节**：
- 多个岗位分别录入同一客户信息（合并为一次录入、多处共享）
- 尽职调查 + 风险评估分开做（合并为一次尽调含风险评估）
- 初审 + 复审由同一级别不同人做（合并或改为抽检）
- 多份申请表重复采集客户基本信息（合并为一表通）

对每个可合并的环节组，标注：
- **合并方案**：如何合并
- **合并后效果**：减少多少步骤/时间
- **实施条件**：需要什么系统或制度支持

#### 3.3 Rearrange · 重排分析

分析步骤顺序是否可以优化：

**判断清单**：
- [ ] 是否有步骤因为串行等待而拉长了总时长？（能否并行）
- [ ] 是否有"先做 A 等 B 结果，再做 C"的流程，而 A 和 C 其实可以并行？（并行化）
- [ ] 是否有审批/检查节点前置导致瓶颈？（后移或前置）
- [ ] 是否可以在流程前端增加筛选/预检，避免无效流程走到后端？（前置过滤器）
- [ ] 是否有步骤的产出不是下一步需要的而是后面某步需要的？（减少中间等待）

**银行流程中常见的重排优化**：
- 尽职调查和征信查询并行（而非先后做）
- 前端预检/预筛选（避免不合格申请进入完整流程）
- 标准化业务走快速通道，复杂业务走完整流程（分流）
- 批量处理（将多次零星处理改为定时批量）

对每个重排建议，标注：
- **重排方案**：新的顺序
- **效果评估**：预计缩短多少时间/等待
- **风险点**：重排后是否引入新的风险

#### 3.4 Simplify · 简化分析

对无法取消、合并、重排的环节，考虑如何简化执行：

**判断清单**：
- [ ] 这个操作是否可以标准化/模板化？（减少自由裁量）
- [ ] 这个判断是否可以规则化/系统化？（减少人工判断）
- [ ] 这个表单是否可以精简字段？（减少填写负担）
- [ ] 这个系统操作是否可以减少点击/跳转？（UI 优化）
- [ ] 这个沟通是否可以用系统通知替代人工通知？（自动化通知）
- [ ] 这个培训/资质要求是否可以降低？（降低执行门槛）

**银行流程中常见的简化优化**：
- 用清单/勾选框替代自由文本填写
- 用规则引擎替代人工合规判断（如黑名单自动拦截）
- 用 RPA/脚本替代重复性系统操作
- 用电子表单替代纸质表单（自动校验、自动流转）
- 用标准化模板替代每次从头撰写

对每个简化建议，标注：
- **简化方案**：具体怎么做
- **预期效果**：减少多少时间/人力
- **实施成本**：需要多少开发/配置工作

### Step 4 · 输出审阅报告

汇总四个维度的分析结果，输出结构化审阅报告。报告模板在 `assets/review-report-template.md`。

报告结构：

```
# [流程名称] ECRS 审阅报告

## 1. 流程概览
- 流程名称、目的、触发条件、产出
- 原始流程：X 个步骤，Y 个角色，预计时长 Z
- 审阅日期、审阅人

## 2. ECRS 审阅摘要
| 维度 | 发现问题数 | 高优先级 | 中优先级 | 低优先级 |
|------|-----------|---------|---------|---------|
| 取消  | X         | X       | X       | X       |
| 合并  | X         | X       | X       | X       |
| 重排  | X         | X       | X       | X       |
| 简化  | X         | X       | X       | X       |

## 3. 详细发现与建议
### 3.1 取消建议
[逐条列出，含依据、风险评估、依赖条件]

### 3.2 合并建议
[逐条列出，含方案、效果、实施条件]

### 3.3 重排建议
[逐条列出，含新顺序、效果评估、风险点]

### 3.4 简化建议
[逐条列出，含方案、预期效果、实施成本]

## 4. 优化后流程设计
[描述优化后的完整流程，标注每一步的 ECRS 改动类型]

## 5. 预期效果
- 步骤数：X → Y（减少 Z%）
- 预计时长：X → Y（缩短 Z%）

- 审批节点：X → Y

## 6. 实施路线图
| 阶段 | 时间 | 内容 | 难度 |
|------|------|------|------|
| 短期 | 1-3月 | 立即可执行的优化 | 低 |

| 长期 | 6-12月 | 需要系统改造的优化 | 高 |

## 7. 风险提示
[列出取消/合并可能带来的合规、风控风险及缓释措施]
```

### Step 5 · 交互修订

向用户展示审阅报告，支持：
- 用户质疑某个判断 → 重新分析并给出更充分的依据
- 用户补充流程细节 → 回到 Step 2 更新模型，重新审阅
- 用户确认报告 → 建议保存为正式文档

### Step 6 · 对照检查清单自检

输出报告前，阅读 `references/checklist.md` 逐项自检，确保：
- 四个维度都已分析，不遗漏
- 每个建议都有依据和风险评估
- 不推荐取消监管强制要求的环节
- 优化后流程仍然完整、可执行
- **长文档场景额外检查**：确认所有分段都已分析，无遗漏片段；跨段建议无重复；全局性问题已识别

## 核心原则

1. **ECRS 顺序不可颠倒** — 必须先 Eliminate，再 Combine，再 Rearrange，最后 Simplify。对本可取消的环节做简化是根本性错误。
2. **合规红线不可碰** — 监管机构明确要求的环节不能建议取消或简化，只能优化执行方式。每次建议取消前，必须确认这不是监管强制要求。
3. **每个建议都要有风险评估** — 银行流程优化不是纯效率问题，必须在风险可控的前提下做。没有风险评估的建议是不完整的。
4. **用事实依据支撑判断** — 不说"这个审批可能没必要"，而说"这个审批的产出 S05 未被后续任何步骤使用，且审批人不具备实质判断所需信息，建议取消"。
5. **优化后的流程必须可执行** — 不能只砍步骤不保证流程完整性。优化后的流程必须从触发条件到最终产出完整闭环。
6. **长文档分段不失真** — 超过 3500 字必须分段，按流程边界切分，每段携带全局上下文。分段分析后再合并，确保不遗漏任何流程细节。
